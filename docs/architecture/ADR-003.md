## 1. Контекст

Практическая работа № 4 просит найти в проекте три точки гонок и выбрать для каждой блокировку, описать токены и показать, как система переживёт несколько копий сервера [1]. Кода ещё нет, поэтому гонки искали в спроектированных операциях модели ПР3. Независимое ревью ПР3 уже указало на три слабых места, и все они оказались гонками или их следствием:

- дубликат завершается до привязки к содержимому; если в этот момент удаляется навсегда последний файл с тем же содержимым, получается доступный файл без байтов (замечание 1);
- место в облаке хранится одним числом, поэтому повторно доставленный `FilePurged` вычитает размер дважды (замечание 2);
- резерв места живёт 10 минут и продлевается событием; если очередь отстанет, резерв снимется у идущей загрузки (замечание 5).

К ним добавилась обычная гонка двух устройств: ноутбук переименовывает файл, телефон в ту же секунду переносит его.

Все гонки мы воспроизвели на PostgreSQL 16.15 и 18.4 скриптом [race-demo.py](race-demo.py): без блокировок данные портятся, с блокировками нет.

## 2. Решение

| № | Решение | Почему |
|---|---|---|
| 1 | Уровень изоляции везде READ COMMITTED, гонки закрываются явными блокировками строк. SERIALIZABLE не используем | в READ COMMITTED команда, наткнувшаяся на изменённую строку, ждёт конца чужой транзакции и перепроверяет условие [2]; SERIALIZABLE потребовал бы повторять всю транзакцию при ошибке 40001 [2], а при загрузке папки из ста файлов конфликтуют почти все |
| 2 | **Место в облаке: пессимистичная блокировка.** Каждая операция начинается с `SELECT ... FROM files.cloud_spaces WHERE owner_id = $1 FOR UPDATE` | конфликты частые (до четырёх загрузок с одного устройства и ещё другие устройства), ошибка дорогая: переполнение; блокировка держится миллисекунды, потому что S3 вызывается вне транзакции [3] |
| 3 | Место учитывается построчно: таблица `files.space_entries` вместо `files.space_reservations`, у каждой строки состояние «зарезервировано» или «занято». Счётчики в `cloud_spaces` меняются той же транзакцией и равны суммам строк | повторные «зарезервировать», «занять», «освободить» находят или не находят строку и ничего не меняют дважды: так подписчики становятся идемпотентными, как требует шаблон outbox [4] |
| 4 | Срок резерва сразу равен сроку загрузки (7 дней). Событие `UploadStarted` его больше не продлевает. Резерв без загрузки снимает фоновая задача через 10 минут, спросив «Загрузку» | правило не зависит от скорости очереди |
| 5 | **Содержимое: пессимистичная блокировка.** Связь С6 стала командой «привязать дубликат»: найти проверенное содержимое по отпечатку, `FOR UPDATE`, сразу записать связь с ID будущего файла. Подписчик `FilePurged` тоже начинает с `FOR UPDATE` той же строки и удаляет содержимое, только если связей не осталось | конфликт редкий, но цена ошибки максимальная: потеря файла, ради которой затевался проект; короткая блокировка одной строки почти ничего не стоит |
| 6 | **Файл и папка: оптимистичная блокировка.** Изменение узла выполняется одной командой `UPDATE ... SET ..., version = version + 1 WHERE id = $1 AND version = $2`, ноль строк означает ответ 412 | конфликт редкий (один владелец, два устройства), а держать блокировку базы, пока человек думает, нельзя: между запросами HTTP соединения нет |
| 7 | Access-токен: JWT с подписью HS256, заголовок `typ: at+jwt` и `kid`, утверждения `iss`, `aud`, `sub`, `sid`, `iat`, `exp`, срок 15 минут. Роли, имени и email в токене нет | рекомендации RFC 8725: проверять алгоритм, издателя и получателя, указывать тип, не брать пароль ключом HMAC [5]; значение `at+jwt` взято из профиля RFC 9068 [7], но обязательные там для OAuth `client_id` и `jti` нам не нужны; payload только кодируется base64url, его может прочитать кто угодно [6]. HS256 достаточно, пока токен выпускает и проверяет один и тот же код; асимметричная подпись нужна, когда токен будет проверять отдельный сервис |
| 8 | Refresh-токен: 256 случайных бит в cookie `HttpOnly; Secure; SameSite=Strict; Path=/api/v1/auth/tokens` на 30 дней, одноразовый. В базе только SHA-256 и только текущий ключ сеанса (белый список) | скрипт страницы cookie не прочитает [8], на другие пути и с чужих сайтов она не уйдёт; ротация и обнаружение повтора по RFC 9700 [9]; выход закрывает сеанс одной строкой, хранить список отозванных токенов не нужно |
| 9 | Горизонтальное масштабирование: балансировщик Nginx ×2, копии API ×N и обработчиков ×M без состояния, PostgreSQL с горячей репликой, Garage из трёх узлов, Redis для счётчиков частоты (схема [scaling.png](scaling.png)) | копию можно убрать или добавить, ничего не потеряв: токен проверяется по подписи, все данные в хранилищах; задачи между обработчиками делит блокировка строк очереди [10]; Garage рекомендует коэффициент репликации 3 [11] |
| 10 | В Redis лежат только счётчики попыток входа и частоты запросов с TTL, общие для всех копий API (`INCR` и `EXPIRE` одной транзакцией [12]). Сеансы, незавершённые загрузки и очередь остаются в PostgreSQL | пять неверных паролей должны считаться на всех копиях вместе, а не на каждой отдельно; потеря счётчиков безопасна, потеря загрузки, которая живёт 7 дней, нет |
| 11 | **Порядок блокировок** (добавлено по итогам независимого ревью ПР4). Транзакция, которой нужно несколько строк, берёт их в одном порядке: строка `files.history_counters` владельца (если операция меняет папки или файлы), затем корень агрегата `FOR UPDATE`, затем строки внутри агрегата. Родительскую папку при добавлении узла и переносе берём `FOR SHARE`. При ошибке 40P01 (deadlock) транзакция повторяется до трёх раз | ревью воспроизвело два deadlock между операциями, которые брали те же строки в разном порядке, и цикл папок при встречном переносе; строка счётчика истории и так сериализует изменения владельца (ADR-002, решение 7), поэтому через неё дерево блокируется без новой таблицы [3] |

## 3. Рассмотренные варианты

- **SERIALIZABLE для всех транзакций.** Корректно без размышлений о блокировках, но каждая гонка превращается в откат и повтор. В нагрузочном прогоне `race-demo.py` сто резервов из одной папки конфликтуют почти все.
- **Оптимистичная блокировка места в облаке** (версия у строки `cloud_spaces`). При сотне одновременных загрузок большинство попыток проигрывает и повторяется, нагрузка на базу растёт вместе с конфликтами. По правилу лекции 5 частые конфликты и дорогая ошибка означают пессимистичную блокировку [13].
- **Атомарный `UPDATE ... SET reserved_bytes = reserved_bytes + n WHERE ... <= allocated`** без `FOR UPDATE`, вместе с `INSERT ... ON CONFLICT DO NOTHING` в `space_entries`. Тоже корректно и даже чуть быстрее: ревью получило те же 51 из 100. Мы оставили `FOR UPDATE`, потому что правило места тогда проверяет корень агрегата в коде, а не условие в SQL, и все операции с местом пишутся одинаково.
- **Распределённая блокировка в Redis.** Лишняя система на пути каждой записи; строка PostgreSQL уже даёт ту же блокировку в той же транзакции, что и изменение.
- **Липкие сессии на балансировщике.** Не нужны: у копий API нет состояния, отказ копии не выкидывает пользователя.

## 4. Последствия

Что получаем:

- три гонки воспроизводятся и закрываются на живой базе: из ста одновременных загрузок по 200 МиБ при 10 ГиБ без блокировки принимаются все сто, с блокировкой ровно 51 ([race-demo-output.txt](race-demo-output.txt));
- замечания 1, 2 и 5 ревью ПР3 закрыты;
- [schema-checks.sql](schema-checks.sql) содержит 84 проверки, все проходят на PostgreSQL 16.15 и 18.4;
- любую копию API или обработчика можно перезапустить во время работы.

С чем соглашаемся:

- резервы одного владельца выстраиваются в очередь на строке `cloud_spaces`; при ста одновременных резервах это сотни миллисекунд на всех;
- привязка дубликата и создание загрузки идут двумя транзакциями; если вторая не удалась, остаётся связь без файла. Байты при этом не теряются, лишнюю связь находит ночная сверка;
- отключённая учётная запись работает до истечения access-токена, то есть до 15 минут;
- PostgreSQL по-прежнему один на запись; реплика защищает от отказа, но не делит нагрузку.

## 5. Риски

| № | Риск | Что делаем |
|---|---|---|
| Р1 | Две транзакции берут блокировки строк в разном порядке и попадают в deadlock | операции держат по две строки и больше (корень и его строки, счётчик истории), поэтому порядок задан решением 11; если deadlock всё же случится, PostgreSQL обрывает одну транзакцию [3], и она повторяется |
| Р2 | Долгая транзакция держит строку места и тормозит загрузки владельца | S3 и другие сетевые вызовы вне транзакции; `lock_timeout` 2 секунды |
| Р3 | Утечка ключа подписи HS256 позволяет выпускать токены | ключ только в окружении, ротация по `kid` без выхода пользователей |
| Р4 | Redis недоступен | счётчики пропускают запросы, остаётся ограничение частоты в Nginx по IP; входы замедляет Argon2id |

## 6. Когда пересмотреть решение

- Резервы одного владельца ждут друг друга дольше 100 мс в p95: резервировать место пачкой для всей папки.
- Появляется отдельный сервис, которому нужно проверять токены: перейти на асимметричную подпись (EdDSA или RS256) и публиковать открытые ключи.
- Нагрузка на запись упирается в один PostgreSQL: сначала вертикально, затем вынести «Проверку и превью» со своей базой, как записано в ADR-002.
