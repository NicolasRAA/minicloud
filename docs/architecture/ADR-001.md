Формат записи взят у М. Найгарда [1]: контекст, решение, статус, последствия. Мы добавили к нему сравнение вариантов по взвешенным критериям, таблицу рисков и условия, при которых решение надо пересмотреть.

## 1. Контекст

«Мини-облако» продолжает практическую работу № 1. В ней мы разбирали архитектурные причины проблем СберДиска с загрузкой, синхронизацией и сохранностью файлов и сравнивали его с Яндекс Диском, Облаком Mail и Облаком билайн. Теперь проектируем небольшое файловое хранилище, в котором эти места продуманы с самого начала. Реализовывать его будем в следующем семестре.

Первая версия должна уметь:

- хранить файлы в папках, переименовывать и переносить их;
- загружать большие файлы с докачкой после обрыва связи или закрытия вкладки;
- держать удалённое в корзине 30 дней и восстанавливать его;
- выдавать на файл гостевую ссылку со сроком действия и отзывать её;
- работать в браузере на ноутбуке и телефоне как PWA.

Ограничения и допущения:

- разработчиков двое, оба пишут на Python и TypeScript;
- всё работает на одном арендованном виртуальном сервере, управляемых облачных сервисов нет;
- используем только открытое ПО;
- расчётная нагрузка учебного стенда: до 200 пользователей с квотой 10 ГиБ, до 20 одновременных загрузок, файл до 50 ГиБ. Это наши допущения, а не замеры.

## 2. Критерии

| Код | Критерий | Что проверяем | Вес |
|---|---|---|---|
| К1 | Простота разработки | двое могут держать в голове всю систему и отлаживать её на ноутбуке | 0,25 |
| К2 | Надёжность загрузки | докачка, проверка целостности, файлы не теряются при сбоях | 0,25 |
| К3 | Эксплуатация | сколько процессов обслуживать на одном сервере, как снимать копии | 0,20 |
| К4 | Развитие | можно ли потом выделить часть в отдельный сервис без переписывания | 0,15 |
| К5 | Стоимость и лицензии | бесплатно и без привязки к одному поставщику | 0,15 |

Самые большие веса у К1 и К2: первый задаёт размер команды, второй прямо вытекает из выводов ПР1.

## 3. Рассмотренные варианты

- **А. Классический монолит.** Один процесс на FastAPI принимает файлы через себя и пишет их на локальный диск.
- **Б. Модульный монолит с S3.** Один код и два типа процессов (API и фоновый обработчик), метаданные в PostgreSQL, файлы в S3-хранилище Garage. Браузер отправляет части файла прямо в S3 по подписанным ссылкам.
- **В. Микросервисы.** Отдельные сервисы входа, метаданных, загрузки и ссылок, у каждого своя база, между ними брокер сообщений.
- **Г. Облачная платформа.** Функции (serverless) и управляемое объектное хранилище одного облачного провайдера.

Оценки от 1 до 5 ставили вдвоём, итог считается как сумма оценок, умноженных на веса.

| Критерий (вес) | А | Б | В | Г |
|---|---|---|---|---|
| К1 (0,25) | 5: один процесс | 4: два процесса из одного кода и S3 SDK | 1: сеть между сервисами, согласованность данных | 3: локально запускать неудобно |
| К2 (0,25) | 2: байты идут через Python, докачку пишем сами | 5: multipart S3, список частей из ListParts, фоновая проверка хэша | 4: то же, но сложнее транзакции | 4: multipart у провайдера |
| К3 (0,20) | 4: один процесс, но копировать нужно ещё и диск с файлами | 4: пять контейнеров в docker compose | 1: десяток процессов и брокер | 5: своих серверов нет |
| К4 (0,15) | 2: файлы на локальном диске привязывают к одному серверу | 4: модули с явными границами, хранилище уже внешнее | 5 | 4 |
| К5 (0,15) | 5 | 5 | 4: брокеру и мониторингу нужны ресурсы | 2: оплата за запросы и трафик, привязка к провайдеру |
| **Итого** | **3,60** | **4,40** | **2,80** | **3,65** |

Чтобы проверить, не подогнаны ли веса под ответ, мы перебрали все наборы весов с шагом 0,05, в которых каждый критерий весит не меньше 0,05 (3876 наборов). Вариант Б занимает первое место или делит его в 3570 наборах (92 %). Он уступает только в трёх случаях:

- простота весит 0,30 и больше, а надёжность загрузки не больше 0,15: выигрывает А;
- эксплуатация весит 0,30 и больше, а стоимость не больше 0,15: выигрывает Г;
- развитие весит 0,65 и больше: выигрывает В.

Нашему проекту ни один из этих наборов не подходит: надёжная загрузка и есть то, ради чего он затевался.

## 4. Решение

Выбираем вариант Б, модульный монолит. Это совпадает с советом М. Фаулера не начинать новый проект с микросервисов [2].

- **Серверная часть:** Python 3.13 и FastAPI. Модули `auth`, `nodes`, `uploads`, `shares`, `changes`. Модуль обращается к другому только через его публичный интерфейс; правило проверяет import-linter в CI [3].
- **Процессы:** один Docker-образ, два режима запуска: API (Uvicorn) и фоновый обработчик (worker Procrastinate).
- **База:** PostgreSQL 18 [4] хранит метаданные, журнал изменений и очередь задач Procrastinate. Задача ставится той же транзакцией, что и изменение данных [5]; это шаблон transactional outbox [6] без отдельного брокера.
- **Файлы:** S3-совместимое хранилище Garage с лицензией AGPLv3 [7]; в нём есть multipart-загрузка, подписанные ссылки и CORS [8]. MinIO не берём: репозиторий его открытой версии архивирован 25.04.2026 и больше не поддерживается [9].
- **Веб-сервер:** Nginx завершает TLS, отдаёт статику PWA, проксирует запросы к API и к Garage, ограничивает частоту запросов.
- **Клиент:** PWA на React и TypeScript. Хэш и отправка частей выполняются в Web Worker, очередь загрузок хранится в IndexedDB.

Частные решения, из которых складывается вариант Б:

| № | Вопрос | Решение | Почему |
|---|---|---|---|
| 1 | Как передаются байты | браузер кладёт части прямо в S3 по подписанным ссылкам, API получает только метаданные | Python-процессы не держат гигабайтные потоки, принятые части хранит S3 |
| 2 | Как продолжить загрузку | список принятых частей сервер берёт из S3 (ListParts); активную сессию можно найти по папке, имени и хэшу | состояние не расходится после сбоев; Safari удаляет данные сайта, если семь дней пользоваться браузером и не заходить на сайт [10] |
| 3 | Какой хэш считать | SHA-256 блоков по 4 МиБ, затем SHA-256 от их склейки, как в content hash Dropbox [11] | `SubtleCrypto.digest()` не умеет считать хэш потоком, файл пришлось бы целиком держать в памяти [12] |
| 4 | Когда файл готов | сначала статус `verifying`, фоновая задача сверяет хэш и ставит `available` или `corrupted` | повреждённый файл не доходит ни до владельца, ни до гостя |
| 5 | Дедупликация | только внутри одного владельца | общая дедупликация даёт побочный канал: по тому, передаются ли байты, можно узнать, есть ли такой файл у других [13] |
| 6 | Удаление | корзина на 30 дней, окончательно удаляет фоновая задача | защита от случайного удаления |
| 7 | Одновременные изменения | `ETag` и `If-Match`, ответы 412 и 428 [14; 15] | две вкладки не затирают изменения друг друга |
| 8 | Повтор запросов | идемпотентность за счёт естественных ключей, без отдельной таблицы ключей | меньше кода и сущностей |
| 9 | Вход | JWT на 15 минут в памяти вкладки, refresh-токен в cookie HttpOnly с ротацией [16]; пароли в Argon2id (19 МиБ, 2 прохода) [17] | украденный через XSS access-токен живёт недолго, повтор refresh-токена заметен |
| 10 | Гостевые ссылки | токен 256 бит, в базе только SHA-256, срок до 30 дней | утечка базы не раскрывает действующие ссылки |
| 11 | Синхронизация вкладок и устройств | лента `/changes` по журналу `node_events` с курсором; номера событий растут, но идут с пропусками [18] | клиент догоняет изменения без полной перезагрузки дерева |
| 12 | Формат ошибок | `application/problem+json` [19] | один формат ошибок на весь API |

## 5. Последствия

Что получаем:

- все изменения метаданных укладываются в одну транзакцию PostgreSQL, распределённых транзакций нет;
- трафик файлов идёт мимо Python-процессов, поэтому скромный сервер выдерживает много загрузок сразу;
- система разворачивается командой `docker compose up` на одном сервере, контейнеров пять;
- если понадобится отдельный сервис, границы модулей уже есть; первый кандидат: обработка файлов (проверка хэша и превью).

С чем соглашаемся:

- PostgreSQL и Garage работают в одном экземпляре, и отказ сервера останавливает систему целиком. Данные защищают RAID1 на сервере, WAL-архив базы и ночная копия файлов в другом дата-центре;
- границы модулей держатся на проверке import-linter и на дисциплине, а не на сети;
- подписанная ссылка, пока не истекла, открывает объект любому, у кого она есть. Поэтому ссылка на скачивание живёт 5 минут, ссылка на загрузку части один час;
- события одного пользователя упорядочены блокировкой его строки в `users`, и одновременные записи одного пользователя встают в очередь. Транзакции короткие, вызовы S3 выполняются вне транзакции.

## 6. Риски

| № | Риск | Вероятность | Влияние | Что делаем |
|---|---|---|---|---|
| Р1 | Garage распространён меньше, чем Ceph или MinIO; возможны отличия в поддержке S3 API | средняя | высокое | работаем через стандартный S3 SDK, интеграционные тесты гоняем против Garage; при проблемах меняем хранилище, API сервиса при этом не меняется |
| Р2 | Сбой между `CompleteMultipartUpload` и записью в базу: объект собран, а файла в базе нет | низкая | среднее | повторное завершение проверяет объект через `HeadObject`; фоновая задача разбирает сессии, застрявшие в статусе `completing` |
| Р3 | Две вкладки одновременно обновляют refresh-токен, срабатывает защита от повтора, и пользователя выкидывает из системы | средняя | среднее | вкладки договариваются через Web Locks API [20]; сервер 30 секунд принимает повтор старого токена |
| Р4 | Браузер стирает локальную очередь загрузок (Safari, режим инкогнито) | средняя | низкое | сервер находит активную сессию по папке, имени и хэшу: пользователь выбирает файл ещё раз, и загрузка идёт с места обрыва |
| Р5 | Очередь задач и журнал изменений нагружают PostgreSQL | низкая | среднее | события старше 90 дней удаляются, задачи короткие; при росте очередь переезжает в отдельную базу |
| Р6 | Потеря сервера целиком | низкая | высокое | WAL-архив и ночные копии в другом дата-центре; файлы, загруженные после последней ночной копии, в этом случае пропадут |
| Р7 | Утечка базы данных | низкая | высокое | пароли в Argon2id, refresh-токены и токены ссылок хранятся только как SHA-256 |

## 7. Когда пересмотреть решение

- Над системой работают больше двух команд или одному модулю нужен свой цикл выпуска.
- Фоновые задачи заметно тормозят API, например p95 времени ответа держится выше 300 мс из-за нагрузки на базу.
- Файлы перестают помещаться на один сервер: переходим на кластер Garage из трёх узлов или на внешнее S3.
- Нужен настольный клиент с синхронизацией папок: ленте изменений понадобится push-канал (WebSocket или long polling).
- Garage перестаёт развиваться: переезжаем на другое S3-хранилище без изменения API.
