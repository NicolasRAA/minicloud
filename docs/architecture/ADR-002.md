## 1. Контекст

В практической работе № 3 мы построили модель «Мини-облака» методами DDD [1; 2]: единый язык, пять ограниченных контекстов, агрегаты с инвариантами и доменные события. Модель описана в [docs/domain/model.md](../domain/model.md). Сверка модели с паспортом ПР2 показала, что паспорт ей противоречит:

- модули ADR-001 (`auth`, `nodes`, `uploads`, `shares`, `changes`) нарезаны по таблицам, а не по языку: проверка содержимого жила внутри фонового обработчика без своей модели, а лента изменений была отдельным модулем;
- завершение загрузки одной транзакцией меняло таблицы трёх будущих контекстов: сессию загрузки, содержимое, узел и журнал;
- удаление папки ставило пометку каждому потомку, то есть папка на 10 000 файлов давала транзакцию на 10 000 строк;
- любая запись пользователя ждала блокировку его строки в `users`, потому что на ней держался порядок ленты изменений;
- квота жила в `users` и никак не учитывала загрузки, которые ещё идут.

Независимое ревью ПР2 (раздел «След работы с ИИ») нашло ещё четыре проблемы модели данных, и их тоже закрывает это решение: окончательное удаление упиралось во внешние ключи `upload_sessions` (замечание 1), база не проверяла владельца и тип связанных записей (замечание 3), порядок ленты держался на соглашении (замечание 6), не было правил для двух одновременных загрузок одного содержимого и для повтора refresh-токена в окне 30 секунд (замечание 10).

## 2. Решение

| № | Решение | Почему |
|---|---|---|
| 1 | Один контекст = один модуль = одна схема PostgreSQL: `auth`, `files`, `uploads`, `content`, `shares`. Журнал событий в схеме `events`, это транспорт, а не контекст | граница будущего сервиса проведена и в коде, и в данных; первый кандидат на вынос из ADR-001 (обработка файлов) теперь отдельный контекст «Проверка и превью» |
| 2 | Внешние ключи только внутри контекста. Между контекстами ссылки по ID без внешних ключей. Исключение: `owner_id` везде ссылается на `auth.accounts` с `ON DELETE CASCADE` | агрегаты ссылаются друг на друга по идентификатору [3]; все контексты принимают ID учётной записи как есть (Conformist), а удаление учётной записи должно стирать данные одной командой |
| 3 | Одна транзакция меняет один агрегат. Событие пишется в `events.journal` той же транзакцией, фоновый обработчик раздаёт его подписчикам через Procrastinate, подписчики идемпотентны | правило Вернона [3] и шаблон transactional outbox [4]; транзакции короткие, событие не теряется при сбое |
| 4 | Команда «загрузить» сразу выдаёт ID будущего файла. Завершение загрузки отвечает `202 Accepted` [5]: файл создаёт контекст «Файлы», получив `UploadCompleted` | загрузка не знает, как устроены папки; повторная доставка события не создаст второй файл, потому что ID один |
| 5 | Место в облаке стало агрегатом: `files.cloud_spaces` и резервы `files.space_reservations`. База проверяет `used + reserved ≤ allocated` | места не может не хватить посреди загрузки; блокируется только строка места, а не весь пользователь |
| 6 | В корзину помечается только узел, который удалили явно. Удаление навсегда ставит `purging_since`, поддерево стирается порциями снизу вверх, на каждый файл публикуется `FilePurged`. Узел внутри, удалённый раньше отдельно, переезжает в корень и живёт свой срок | короткие транзакции для папки любого размера; каждый файл освобождает место и содержимое своим событием |
| 7 | История: номер записи выдаёт счётчик владельца `files.history_counters` командой `INSERT ... ON CONFLICT DO UPDATE ... RETURNING` | номера без пропусков и в порядке фиксации; блокируется только счётчик истории, а не строка пользователя |
| 8 | Содержимое стало агрегатом: связь «файл → содержимое» хранится в `content.content_files`. Пока содержимое проверяется, может появиться копия от параллельной загрузки; после проверки копия сливается с проверенным, а лишний объект удаляется | правило дубликатов живёт в одном месте; база гарантирует одно проверенное содержимое на отпечаток |
| 9 | Сеанс входа и цепочка ключей продления (`auth.signin_sessions`, `auth.refresh_keys`): действует только последний ключ. Повтор старого ключа в течение 30 секунд выдаёт следующий ключ цепочки, позже закрывает этот сеанс как украденный | цепочка не ветвится [6]; кража закрывает один сеанс, а не все входы пользователя |
| 10 | Составные внешние ключи по `(id, owner_id, type)` и `(id, owner_id)`; имена в форме NFC (`name IS NFC NORMALIZED`) [7; 8] | база отклоняет папку в чужой папке, папку внутри файла и чужое содержимое; два одинаковых на вид имени в одной папке не уживаются |

Список модулей ADR-001 заменяется таким: `auth` (Вход), `files` (Файлы, вместе с историей), `uploads` (Загрузка), `content` (Проверка и превью), `shares` (Гостевой доступ) и адаптер хранилища `storage`. Контракт API обновлён до версии 1.1: термины из единого языка, `202` на завершение загрузки, `cloud_space` в профиле, история с номерами без пропусков.

## 3. Рассмотренные варианты

- **А. Оставить одну общую схему ПР2** и только переименовать модули. Дёшево, но транзакции по-прежнему проходят через три контекста, и выделить «Проверку и превью» в сервис без переписывания схемы нельзя.
- **Б. Схема на контекст, связи событиями** (выбрано). Одна база, одна резервная копия, а граница видна в данных.
- **В. Отдельная база на контекст.** Самая жёсткая граница, но для двоих разработчиков и одного сервера это пять баз, пять копий и распределённые сценарии восстановления. Схемы дают ту же границу без этих затрат.

## 4. Последствия

Что получаем:

- каждая операция меняет один агрегат и укладывается в короткую транзакцию;
- база держит второй рубеж правил модели: 76 проверок в [schema-checks.sql](schema-checks.sql) проходят на PostgreSQL 16.15 и 18.4;
- событие не теряется: оно записано той же транзакцией, что и изменение;
- устройство не пропустит изменение: номера истории идут подряд.

С чем соглашаемся:

- файл появляется в папке не в момент ответа на «завершить», а когда «Файлы» обработают событие, обычно через доли секунды. Клиент показывает файл сразу по данным загрузки;
- таблиц стало 13 вместо 7, каждое изменение в «Файлах» пишет две записи: в историю для человека и в журнал для подписчиков;
- согласованность ссылок между контекстами держат события и код, а не внешние ключи. Ночная задача сверяет занятое место с суммой размеров файлов;
- счётчик истории сериализует изменения одного владельца. Это осознанная пессимистичная блокировка там, где ошибка дорогая, а транзакции короткие.

## 5. Риски

| № | Риск | Что делаем |
|---|---|---|
| Р1 | Подписчик упал и не обработал событие | событие остаётся в журнале без `dispatched_at`, задача повторяется; событие старше пяти минут без обработки видно в мониторинге |
| Р2 | Долгий подписчик держит счётчик истории и тормозит другие изменения владельца | обращения к S3 выполняются вне транзакции, подписчики пишут только свои строки |
| Р3 | Занятое место разошлось с суммой размеров файлов | ночная сверка пересчитывает `used_bytes` и `reserved_bytes` и пишет расхождение в журнал |
| Р4 | Пользователь не видит файл сразу после «завершить» и думает, что он потерялся | ответ 202 содержит `file_id`, клиент показывает файл с пометкой «проверяется», пока он не придёт из истории |

## 6. Когда пересмотреть решение

- Задержка между `UploadCompleted` и появлением файла заметна пользователям (p95 больше секунды): обработчик «Файлов» вызывать сразу после фиксации, журнал оставить страховкой.
- У одного владельца сотни изменений в секунду и счётчик истории стал узким местом: номера истории выдавать по снимку транзакций (`pg_snapshot_xmin`) без блокировки.
- «Проверка и превью» выносится в отдельный сервис: журнал заменяется брокером сообщений, каталог событий остаётся тем же.
